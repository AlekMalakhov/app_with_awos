## 1. High-Level Technical Approach

This feature enables writing generated acceptance criteria back to Jira ticket descriptions. The implementation will:

1. **Extend `JiraClient`** with a new `update_description()` method that uses the Jira REST API v3 `PUT /rest/api/3/issue/{key}` endpoint
2. **Create an AC formatting module** (`src/jira/ac_formatter.py`) that converts acceptance criteria into Atlassian Document Format (ADF)
3. **Implement validation and retry logic** using the existing `tenacity` patterns
4. **Integrate with `PollingService`** at the AC generation placeholder to write back results

The approach maintains consistency with existing codebase patterns for error handling, logging, and testing.

## 2. Proposed Solution & Implementation Plan (The "How")

### 2.1 New Module: AC Formatter

**File:** `src/jira/ac_formatter.py`

**Purpose:** Convert acceptance criteria into Atlassian Document Format (ADF) and manage description updates.

**Functions:**

| Function | Input | Output | Purpose |
|----------|-------|--------|---------|
| `format_acs_to_adf()` | `List[str]` | `dict` (ADF node) | Convert AC list to ADF with heading + checkboxes |
| `append_acs_to_description()` | `dict` (existing ADF), `List[str]` | `dict` (merged ADF) | Append new ACs to existing description |
| `build_attribution_node()` | None | `dict` (ADF node) | Generate attribution with human-friendly timestamp |

**ADF Structure for ACs:**

```json
{
  "type": "doc",
  "version": 1,
  "content": [
    {
      "type": "heading",
      "attrs": { "level": 2 },
      "content": [{ "type": "text", "text": "Acceptance Criteria" }]
    },
    {
      "type": "taskList",
      "attrs": { "localId": "..." },
      "content": [
        {
          "type": "taskItem",
          "attrs": { "localId": "...", "state": "TODO" },
          "content": [{ "type": "text", "text": "AC text here" }]
        }
      ]
    },
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "Generated by Jira AC Assistant on ", "marks": [{ "type": "em" }] },
        { "type": "text", "text": "January 15, 2024 at 2:30 PM UTC", "marks": [{ "type": "em" }] }
      ]
    }
  ]
}
```

### 2.2 JiraClient Extension

**File:** `src/jira/client.py`

**New Method:** `update_description()`

```python
async def update_description(self, issue_key: str, description_adf: dict) -> bool:
    """
    Update the description field of a Jira ticket.

    Args:
        issue_key: The Jira issue key (e.g., "PROJ-123")
        description_adf: The new description in ADF format

    Returns:
        True if update succeeded, False otherwise

    Behavior:
        - Validates issue_key is non-empty
        - Uses PUT /rest/api/3/issue/{key} endpoint
        - Retries up to 3 times with exponential backoff
        - Logs errors on failure
    """
```

**Retry Configuration:**
- Max attempts: 3 (via existing `JIRA_MAX_RETRIES` setting)
- Backoff: Exponential (1s, 2s, 4s, max 16s)
- Retry conditions: 5xx errors, 429 rate limit, connection errors, timeouts
- No retry: 4xx client errors (except 429), auth errors

**HTTP Request:**
```
PUT /rest/api/3/issue/{issueIdOrKey}
Content-Type: application/json
Authorization: Basic {encoded_credentials}

{
  "fields": {
    "description": { ...ADF content... }
  }
}
```

**Expected Response:** `204 No Content` on success

### 2.3 Validation Logic

**Location:** `src/jira/ac_formatter.py`

**Function:** `validate_acs()`

| Validation | Behavior |
|------------|----------|
| Empty AC list | Return `False`, log warning with ticket ID |
| Non-string AC items | Filter out, log warning |
| Valid | Return `True` |

**Updated flow:**
```python
# 1. Generate ACs (placeholder for now)
generated_acs = ["AC 1", "AC 2", "AC 3"]  # Will be replaced by AI generation

# 2. Validate ACs
if not validate_acs(generated_acs, ticket.key):
    logger.warning("No valid ACs to write for %s", ticket.key)
    return

# 3. Get current description
current_ticket = await self._jira_client.get_ticket(ticket.key)

# 4. Format and append ACs
updated_description = append_acs_to_description(
    existing_adf=current_ticket.description_adf,
    new_acs=generated_acs
)

# 5. Write back to Jira
success = await self._jira_client.update_description(ticket.key, updated_description)
if success:
    logger.info("Successfully wrote ACs to %s", ticket.key)
else:
    logger.error("Failed to write ACs to %s after retries", ticket.key)
```

## 3. Impact and Risk Analysis

### 3.1 System Dependencies

| Dependency | Impact |
|------------|--------|
| `JiraClient` | Extended with new method; existing functionality unchanged |
| `PollingService` | Calls new write functionality; existing flow preserved |
| `TicketData` model | New optional field; backward compatible |
| Jira REST API | Requires write permission for the API token |

### 3.2 Potential Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| **Jira API token lacks write permission** | Medium | High | Document required permissions; fail gracefully with clear error message |
| **ADF format mismatch** | Low | Medium | Comprehensive unit tests for ADF generation; validate against Jira API docs |
| **Rate limiting on writes** | Low | Medium | Existing retry logic handles 429; consider adding jitter |
| **Large descriptions exceed API limits** | Low | Low | Jira Cloud has no strict limit on description size; monitor for edge cases |
| **Concurrent writes to same ticket** | Low | Medium | Current polling design processes tickets sequentially; not a concern for v1 |
