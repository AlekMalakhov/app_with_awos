# Functional Specification: Write ACs Back to Jira

- **Roadmap Item:** Write ACs Back to Jira — Enable writing generated acceptance criteria to the ticket's AC field.
- **Status:** Completed
- **Author:** Product Analyst

---

## 1. Overview and Rationale (The "Why")

### Problem Statement
After the Jira AC Assistant generates acceptance criteria (whether from AI analysis, Barley context enrichment, or stakeholder approval), those ACs need to be persisted back to the Jira ticket. Without this capability, developers cannot see the generated ACs in their normal workflow, and the entire AC generation process provides no value.

### Desired Outcome
When ACs are generated, they are automatically written to the Jira ticket's description field in a consistent, readable format. Developers opening the ticket will immediately see clear, actionable acceptance criteria alongside the original description.

### Success Criteria
- 100% of successfully generated ACs are written to the corresponding Jira ticket.
- ACs appear in a consistent format across all tickets.
- Failed write operations are retried and logged for investigation.

---

## 2. Functional Requirements (The "What")

### 2.1. Write Generated ACs to Jira Description

- **As a** developer, **I want** generated acceptance criteria to appear in the Jira ticket description, **so that** I can see what "done" looks like without leaving Jira.

  - **Acceptance Criteria:**
    - [x] When ACs are generated, they are appended to the ticket's existing description field.
    - [x] ACs are formatted with an `## Acceptance Criteria` heading followed by checkbox items (`- [ ] ...`).
    - [x] A small attribution note is added below the ACs indicating they were auto-generated (e.g., "_Generated by Jira AC Assistant_").
    - [x] The original ticket description content is preserved and not modified.

### 2.2. Handle Existing ACs in Description

- **As a** Product Owner, **I want** to be able to regenerate ACs without losing previously generated ones, **so that** I can iteratively refine the criteria.

  - **Acceptance Criteria:**
    - [x] If an `## Acceptance Criteria` section already exists in the description, new ACs are appended below the existing ones.
    - [x] Previously generated ACs remain intact and are not removed or modified.
    - [x] Each set of appended ACs includes its own attribution timestamp to distinguish generations.

### 2.3. Validate Before Writing

- **As a** system operator, **I want** the system to validate ACs before writing, **so that** we don't clutter tickets with empty or invalid data.

  - **Acceptance Criteria:**
    - [x] The system does not write to Jira if the generated AC list is empty.
    - [x] If validation fails (empty AC list), the operation is logged with the ticket ID and reason.

### 2.4. Handle Write Failures

- **As a** system operator, **I want** failed write operations to be retried and logged, **so that** transient errors don't result in lost ACs.

  - **Acceptance Criteria:**
    - [x] If the Jira API returns an error, the system retries up to 3 additional times.
    - [x] Retries use exponential backoff between attempts.
    - [x] If all retries fail, the error is logged with ticket ID, error message, and the ACs that failed to write.
    - [x] The system does not crash or halt other operations due to a single ticket's write failure.

---

## 3. Scope and Boundaries

### In-Scope

- Writing generated ACs to the Jira ticket description field.
- Formatting ACs with heading and checkbox items.
- Adding attribution note to generated ACs.
- Appending to existing ACs (not replacing).
- Validation that at least 1 AC exists before writing.
- Retry logic with exponential backoff (up to 3 retries).
- Error logging for failed write operations.

### Out-of-Scope

- **AI-Powered AC Generation** — Separate roadmap item (Phase 1).
- **Manual Re-Trigger Capability** — Separate roadmap item (Phase 1).
- **Barley AI Consultation** — Separate roadmap item (Phase 2).
- **Slack Integration Foundation** — Separate roadmap item (Phase 2).
- **AC Approval Workflow** — Separate roadmap item (Phase 3).
- **Notification & Status Tracking** — Separate roadmap item (Phase 3).
- **Error Handling & Retry Logic (comprehensive)** — Separate roadmap item (Phase 3); this spec covers only the retry logic specific to Jira writes.
- Writing ACs to a custom field (only description field is in scope).
- Slack notification on write failure.
- UI for viewing write operation history.
